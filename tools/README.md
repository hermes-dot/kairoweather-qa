# 天气温度简报（W1/W2 练习）

读取和风天气 `daily` 响应，在终端打印一份温度简报。纯标准库，无第三方依赖。

## 用法

```powershell
# 在仓库根目录执行（uv 会用 pyproject 里锁定的 Python 3.12）
uv run python tools/weather_report.py --file data/fixtures/daily_ok.json

# 第二版：多一张柱状图
uv run python tools/weather_report_v2.py --file data/fixtures/daily_ok.json

# 看帮助
uv run python tools/weather_report_v2.py --help
```

> Windows 终端中文乱码时，先 `chcp 65001`，或设 `$env:PYTHONIOENCODING="utf-8"`。

## 测试（W2）

测试文件在 [`../tests/test_weather_report.py`](../tests/test_weather_report.py)：
**11 条测试函数 / 参数化后 19 个用例**，覆盖 5 个入口。

| 被测函数 | 用例 | 关键断言 |
|---|---|---|
| `load_daily` | 5 | 正常 3 天；文件缺失、JSON 损坏、业务码非 200、`daily` 空/缺失都干净失败 |
| `to_float` | 2（7 组参数） | 合法数字串（含负数、首尾空格）；脏数据报错必须带「第几天 + 字段 + 原始值」 |
| `analyze` | 2 | 极值、平均、最大温差；单日且全同温时不除零 |
| `render` | 1 | 首行日期区间、每天一行、柱子长度随温度递减 |
| `main` | 1 | stdout 有完整报表；文件缺失时干净失败，不输出半截报表 |

```powershell
# 只跑这 19 条
uv run pytest tests/test_weather_report.py -q

# 或跑全量默认档（当前 59 条；5 条 live 默认排除）
uv run pytest -q
```

> **为什么脚本在 `tools/`、测试在 `tests/`**：`qa/pyproject.toml` 的 `testpaths = ["tests"]` 只收集 `tests/`，
> 把用例放进去就能被 `pytest -q` 自动带上；脚本放 `tools/`，因为它是被测的独立小工具，
> 不属于 `api/`（请求层），也不属于 `mock/`（假服务）。
>
> **为什么不用 `tmp_path`**：部分受限环境里系统临时目录不可写，pytest 建目录会直接 `WinError 5`。
> 用例改用 `workdir` fixture，在仓库的 `tmp_tests/` 下建独立目录、收尾即删；普通机器上换回 `tmp_path` 也可以。

### W2 的两条结论

1. **纯函数先测数字，再测文本**：`analyze` 直接断言 26 / 9 / 17.166…，`render` 才断言字符串。
   如果只有一个 `build_report`，任何格式改动都要重跑全部断言。
2. **非法输入比正常输入更值得写**：5 条 `load_daily` 用例里 4 条在测坏数据；
   真实世界里「文件不存在 / JSON 损坏 / 业务码 404」比「三天天气正常」常见得多。

## 错误处理

所有失败都是**一行中文提示 + 退出码 1**，不给用户甩 traceback。

| 情况 | 输出 |
|---|---|
| 文件不存在 | `找不到文件：..\nope.json` |
| JSON 损坏 | `JSON 解析失败（第 2 行第 1 列）：Expecting value` |
| 业务码不是 200 | `业务码异常：'404'` |
| `daily` 为空或缺失 | `daily 为空或缺失，没有可分析的数据` |
| 温度是脏数据 | `第 1 天 tempMax 不是数字：'abc'` |

## 三个设计取舍

### 1. 为什么拆成四层（load_daily + to_float → analyze → render → main）

每层只回答一个问题：**怎么拿到数据 → 怎么算 → 怎么显示**。
分层的判断标准是「改动时会不会互相牵动」：改柱状图宽度不该碰计算，改平均算法不该碰输出格式。

### 2. 为什么错误用 `SystemExit` + 中文提示，而不是抛 traceback

这是个命令行工具，用户不需要看栈。而且退出码非 0 才能被 shell / CI 判断为失败——
**“给人看的文案”和“给机器看的退出码”两件事都要做对**。

### 3. 为什么 `analyze` 不读文件也不打印

因为纯函数最好测。`analyze(一堆 dict)` → `一个 dict`，测试只要断言数字；
如果它既读文件又打印，W2 写测试时就不得不造临时文件、抓 stdout。
**可测性不是测试阶段才考虑的，是写代码时就决定的。**

## 第一版和第二版的差别

| | 第一版 | 第二版 |
|---|---|---|
| 结构 | `build_report` 既计算又拼字符串 | `analyze` 只计算，`render` 只渲染 |
| 柱状图 | 无 | 有 |
| 可测性 | 只能断言整段文本 | 可以先断言数字，再单独断言文本 |

第二版是多花 20 行换来「计算」和「显示」的解耦。这不是过度设计——
一旦格式要变（加颜色、改成 JSON），第一版每次都得重跑全部断言。

## 已知限制

- 只认 `daily` 数组，不处理 `hourly` / `now`；
- 柱状图按**最高温**画位置，不是「最高到最低」的区间条；
- 平均温 = 所有最高温与最低温的算术平均，**不等于**真实日均温（那需要逐小时数据）；
- 没有 `--json` 输出，也没有 `--top N`。
